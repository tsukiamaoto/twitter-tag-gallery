狀態：done

## 問題與修正

選畫師後的圖片 API 曾兩次超過 35 秒；當時排程與另一個全庫處理程序同時讀寫 D 槽。逐圖 EXISTS 查詢及首次顯示才同步產生縮圖，會進一步放大磁碟競爭。

- `background_work.py`：使用 OS 檔案鎖做跨程序互斥，涵蓋 Web、Windows 排程、AI 批次、Pixiv 批次、批次反查、MCP 批次及 CLI。非同步啟動先保留鎖，再回覆 started；巢狀步驟共用同一流程的鎖，其他執行緒不能加入。程序離開後由 OS 釋放。
- 排程時段另外持久化去重；Windows `--run-once` 與程式內時鐘使用相同時段鍵，第一個流程完成後也不會重跑同一時段。
- 圖片讀取跨程序最多兩個，背景只可使用其中一個。AI 預處理由六個執行緒降為兩個、預取批次由 48 降為 8；網路批次並行數降為 2。瀏覽時背景工作會讓出時間。MD5 改成分塊讀取。
- 主題標籤整理只補缺少的關聯，以 500 筆分批短交易寫入，讓出時間時不持有寫入交易；只更新相關主題計數。沒有新增／移除圖片的索引掃描不重算全庫計數。
- `/api/images` 使用 tag_id 索引先找候選 image_id，保留多標籤交集、排除及未知標籤語意。自然排序先取 id／路徑，再讀當頁完整資料；查詢使用一致的讀取快照，錯誤時也關閉連線。
- `thumbnail_cache.py`：有界佇列、兩個 worker，其中一個保留給畫面請求；同張圖的請求共用工作，跨程序亦有每張圖的鎖。暫存 JPEG 完成後原子改名；依來源路徑、檔案大小及奈秒修改時間分版，來源更新會失效。沿用有效的既有 JPEG，支援 ETag／304。
- 圖片列表只排入預取 ID，不在查詢請求內解碼圖片。另在瀏覽與重型任務都閒置時，逐張補齊舊圖庫縮圖；新增圖片也會接續處理。背景預取最多占一半佇列，保留可見圖片的容量。
- 縮圖等待使用 async future，不占用 FastAPI 同步工作執行緒；瀏覽器取消不會取消其他請求共用的縮圖。損壞圖片回傳錯誤，不退回傳送大型原圖。
- 左欄選取／清除標籤直接更新已載入清單，不再重新請求 `/api/tags`；較舊的分類回應不能蓋過新分類。

## 限制

磁碟快取與背景負載會變動，以上不是相同負載的嚴格前後對照，也不保證所有操作的最大延遲。首次縮圖仍須讀取與解碼來源；修正限制其資源占用、提前預取並優先處理可見圖片。日後由其他入口啟動的長工作，也必須使用同一任務鎖與媒體讀取限制。
